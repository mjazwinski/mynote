# Research: Category Notes Canvas

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-11-18

All Technical Context items are resolved below. Each entry lists the decision, why it was
chosen, and the alternatives considered.

## R1. Python version

- **Decision**: Python 3.12 minimum (container image `python:3.12-slim`).
- **Rationale**: User requested "python 3.1.12 at least", interpreted as 3.12 (3.1.12 is not a
  released version). 3.12 has mature `asyncio` (TaskGroup, faster event loop) and is supported
  by FastAPI, Pydantic v2 and PyMongo.
- **Alternatives**: 3.13 — also fine, code MUST stay compatible with it; not required.

## R2. Async MongoDB driver

- **Decision**: PyMongo's native async API (`pymongo.AsyncMongoClient`, PyMongo ≥ 4.13).
- **Rationale**: Officially supported asyncio driver from MongoDB; Motor is deprecated in its
  favour. Fully async, fits FastAPI's event loop.
- **Alternatives**: Motor (deprecated); Beanie/ODMantic ODMs (extra abstraction not needed for
  two collections).

## R3. Web framework & API style

- **Decision**: FastAPI with async route handlers, Pydantic v2 schemas, served by Uvicorn.
  REST resources under `/api/v1`. OpenAPI document generated by FastAPI and kept in sync with
  [contracts/openapi.yaml](./contracts/openapi.yaml).
- **Rationale**: Requested by user; satisfies constitution Principle I (documented HTTP API).
- **Alternatives**: Litestar, Starlette (not requested).

## R4. Structured logging

- **Decision**: Standard-library `logging` configured via `logging.config.dictConfig` with a
  small custom `JsonFormatter` (subclass of `logging.Formatter`) emitting one JSON object per
  line to stdout. Fields: `timestamp` (ISO-8601 UTC), `level`, `logger`, `message`,
  `request_id`, plus any `extra={...}` keys. A request-ID middleware stores the ID in a
  `contextvars.ContextVar`; a `logging.Filter` injects it into every record. Uvicorn loggers are
  routed through the same handler. Level set via `LOG_LEVEL` env var.
- **Rationale**: User asked for structured logging using Python `logging`; JSON on stdout is
  the container-native pattern (`docker logs`, log collectors). No third-party dependency.
- **Alternatives**: `structlog`, `python-json-logger` (extra dependency, not needed).

## R5. Note ordering

- **Decision**: Each note stores an integer `position` (0-based) within its category. Reorder is
  done by `PUT /categories/{id}/notes/order` with the complete ordered list of note IDs; the
  server validates that the list is exactly the category's note set and rewrites positions
  with a single `bulk_write`.
- **Rationale**: Simple, idempotent, trivially guarantees "within category only" (IDs from other
  categories are rejected). At ≤ 200 notes per category the payload is tiny.
- **Alternatives**: Fractional/lexicographic ranks (single-document updates, but more complex
  and needs rebalancing); linked list (fragile).

## R6. Category delete cascade without transactions

- **Decision**: `DELETE /categories/{id}` deletes the category's notes first, then the category.
  MongoDB runs as a standalone container (no replica set), so no multi-document transaction.
- **Rationale**: If the process fails between steps, the category still exists (possibly with
  fewer notes) and the user can retry — no orphaned notes are left behind. Avoids running a
  replica set just for this.
- **Alternatives**: Single-node replica set + transaction (stronger atomicity, more ops
  complexity); delete category first (risks orphaned notes).

## R7. Unique category names

- **Decision**: Store `name` (trimmed, as typed) and `name_key` (`name.casefold()`); unique index
  on `name_key`. Duplicate insert → `409 Conflict`.
- **Rationale**: Enforces FR-001 case-insensitive uniqueness atomically in the database.
- **Alternatives**: Collation-based unique index (works but less explicit); app-level check only
  (race-prone).

## R8. Frontend stack

- **Decision**: React 19 + TypeScript, built with Vite. Tailwind CSS v4. Theme tokens defined as
  CSS custom properties in `src/styles/theme.css` (`:root` = light, `.dark` = dark) and exposed to
  Tailwind via `@theme`; components use only token-based utilities (e.g., `bg-surface`,
  `text-fg`), never raw palette colors.
- **Rationale**: User requested React + Tailwind; CSS-variable tokens satisfy constitution
  Principle III (centralized tokens, no hard-coded colors). TypeScript catches API-contract drift.
- **Alternatives**: Plain JS (less safety); CSS Modules (not requested).

## R9. Dark mode

- **Decision**: Class strategy — `dark` class on `<html>`. Initial value: stored preference in
  `localStorage` (`mynote.theme`), else `prefers-color-scheme`. Small inline script in
  `index.html` applies it before first paint to avoid flash.
- **Rationale**: Meets FR-023; user toggle overrides system preference.

## R10. Drag-and-drop reordering

- **Decision**: `@dnd-kit/core` + `@dnd-kit/sortable` with Pointer, Touch and Keyboard sensors.
  Additionally explicit "move up / move down" buttons on each note (FR-021). Drop targets are
  limited to the current canvas's sortable context, so dropping on a tab does nothing.
- **Rationale**: Works with mouse, touch (tablets) and keyboard; accessible announcements.
- **Alternatives**: Native HTML5 DnD (poor touch support); `react-beautiful-dnd` (unmaintained).

## R11. Auto-save & unsaved-change guard

- **Decision**: Client-side `notes` store (React context + `useReducer`) tracks per-note
  `saveState` ∈ {`saved`, `dirty`, `saving`, `error`}. `onBlur` of a note editor triggers
  `PATCH /notes/{id}` if dirty. Dirty content is mirrored to `localStorage` drafts
  (`mynote.drafts`) on every change and cleared on successful save; drafts are restored on load
  (FR-013). Category switch calls `flushAll()` (await all pending saves); on failure a dialog
  offers Retry / Discard & switch / Cancel (FR-012). `beforeunload` handler warns while any note
  is dirty/saving/error (FR-014).
- **Rationale**: Directly implements constitution Principle V.
- **Alternatives**: Debounced save-while-typing (more requests; can be added later on top).

## R12. Data fetching

- **Decision**: Thin typed `fetch` wrapper (`src/api/client.ts`) + the store above; no data-fetching
  library.
- **Rationale**: Two resources, custom dirty-state handling; a library would add little.
- **Alternatives**: TanStack Query (good caching, but dirty/draft logic would still be custom).

## R13. Testing

- **Decision**:
  - Backend: `pytest` + `pytest-asyncio`; unit tests for services/formatter with fakes;
    API/integration tests via `httpx.AsyncClient` (ASGI transport) against a real MongoDB
    started with `testcontainers[mongodb]` (or `MONGODB_URI` pointing to the compose Mongo).
  - Frontend: Vitest + React Testing Library + MSW for unit/component tests (auto-save,
    unsaved guard, confirm dialogs, reorder); Playwright e2e for full flows at tablet
    (800×1280, 1280×800) and 27″ (2560×1440) viewports in light and dark mode.
  - Constitution rule: every function/component with cognitive complexity > 3 MUST have a unit
    test; enforced via review (and `ruff`/`eslint-plugin-sonarjs` cognitive-complexity rule as a
    reporting aid).
- **Rationale**: Covers constitution testing gates and the added testing constraint.

## R14. Containerization & deployment

- **Decision**: Three containers orchestrated with Docker Compose:
  1. `frontend` — multi-stage build: `node:22-alpine` builds the Vite bundle; runtime is
     `nginxinc/nginx-unprivileged:1.27-alpine` serving static files with SPA fallback and reverse-proxying `/api/` to
     the backend (URL from `BACKEND_URL` env via nginx templates). Exposes port 8080, runs
     as non-root.
  2. `backend` — `python:3.12-slim`, multi-stage (build wheel/venv, copy into slim runtime),
     non-root user, `uvicorn mynote.main:app --host 0.0.0.0 --port 8000`. Configured via env
     (`MONGODB_URI`, `MONGODB_DB`, `LOG_LEVEL`, `CORS_ORIGINS`). Healthcheck on
     `/api/v1/health`.
  3. `mongo` — official `mongo:8` image with a named volume; not built by this project.
- **Rationale**: User requirement (separate frontend and backend containers, Mongo in its own
  container). Proxying `/api` through nginx gives same-origin requests, so CORS is only needed
  for local dev.
- **Alternatives**: Backend serving static files (violates two-container requirement); Node
  server for frontend (unnecessary for static SPA).

## R15. Authentication

- **Decision**: None (single-user, per spec Assumptions). Deployment is expected on a trusted
  network.
- **Rationale**: Out of scope for this feature; documented as a known limitation.
